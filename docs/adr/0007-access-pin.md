# 0007. 起動時に表示する 6 桁の PIN で閲覧を制限する

- status: proposed
- date: 2026-10-23

## Context

akapen は、Google Meet などで話しながら URL を共有し、その場で手元にしかないドキュメントを一緒にレビューする使い方を想定している。[ADR-0006](./0006-security-without-auth.md) では認証を持たず、ブラウザ経由の攻撃 (DNS rebinding / CSRF / CSWSH) だけを防いでいる。そのため、URL に届く人 (同じ tailnet の他の人や端末、`--host 0.0.0.0` での LAN 内の人) は誰でもファイルを読めて、コメントもできる。

起動した人が「今この場にいる相手」にだけ見せられるよう、起動時に 6 桁の数字を表示し、参加者は最初の画面で Nickname と一緒にそれを入力してから使えるようにしたい (レビューのコメントでの要望)。

## Decision

**起動するたびに 6 桁の PIN をランダムに作ってターミナルに表示し、最初の画面で PIN を入力した (正しかった) ブラウザにだけ、HttpOnly の Cookie でアクセスを許す。PIN の総当たりは、失敗の回数の上限で防ぐ。** ADR-0006 の対策 (`Host` の許可リスト・書き込みと WebSocket のトークン・`Origin` の検証) はそのまま残す。

設計の要点:

- **PIN**: `crypto.getRandomValues` で `000000`〜`999999` を一様に作る。起動時に URL と並べて `PIN: 123 456` と表示する。プロセスのメモリにだけ持ち、ファイルには書かない
- **ログイン**: `POST /api/login` に `{ pin }` を送る。正しければランダムなトークン (32 バイト) を作ってメモリに覚え、`akapen_auth` の Cookie (`HttpOnly; SameSite=Strict; Path=/`) で返す。比較は定数時間で行う
- **守る範囲**: `/api/*` と `/ws` は Cookie が必要 (無ければ `401`)。例外は `POST /api/login` と、多重起動の判定に使う `GET /api/health` (ルートのパスを返さないようにして、アプリ名・版・セッション ID だけにする)。SPA の HTML と JS・CSS はデータを含まないので Cookie なしで配る
- **総当たり対策**: 失敗は 1 分あたり 5 回まで (超えたら `429`)。プロセス全体で 20 回失敗したら、以後のログインをすべて拒否し、ターミナルに「再起動して新しい PIN を使う」よう表示する。6 桁 (100 万通り) を 20 回で当てられる確率は 0.002%
- **画面**: Cookie が無ければ、最初の画面で Nickname と PIN を一緒に入力する。Cookie があれば (同じ起動の間に再読み込みした場合)、PIN は聞かない
- **起動した本人も PIN を入力する** (同じ画面で扱いを分けない)
- **`akapen export` などの CLI**: DB を直接読むので PIN は要らない (同じマシンのユーザーの権限で動くため)

## Options considered

- **起動ごとの 6 桁の PIN + Cookie** (採用案): 要望どおり、URL とは別の経路 (口頭やチャット) で数字を伝えた相手だけが入れる。Cookie なので `<img src="/api/raw?...">` や WebSocket にも自然に効く — 再起動のたびに全員が入力し直す。6 桁は推測されうるため、失敗の回数の上限が要る
- **セッションごとに固定の PIN** (`session.json` に保存): 再起動しても同じ PIN で、Cookie も使い続けられる — PIN をファイルに残すことになる。一度伝えた PIN がセッションの間ずっと有効になる
- **URL に長いトークンを入れる** (Jupyter 方式 `?token=...`): 入力が要らない — URL だけで入れてしまい、チャットの履歴などから漏れる。「数字を別に伝える」という要望に合わない
- **HTTP Basic 認証で PIN をパスワードにする**: 実装が小さい — ブラウザ標準のダイアログで Nickname と一緒に扱えない。失敗の回数を制御しにくい
- **Tailscale の ID ヘッダー (`Tailscale-User-Login`) の許可リスト**: 入力が要らず強い — `tailscale serve` を通す場合に限られ、Meet の相手が tailnet にいるとは限らない。v2 の候補として残す

## Consequences

- URL を知っているだけの人は、ファイルもコメントも見られなくなる。PIN を伝えた相手だけが使える
- 再起動すると、全員が PIN を入力し直す (Cookie のトークンはメモリにしか無いため)
- E2E テストは、ログインの手順か、テスト用に PIN を固定する起動の方法が要る
- PIN は 6 桁しかないので、URL に届く攻撃者の総当たりは、失敗の回数の上限に頼る。上限に達したら再起動が要る (利用者が気づけるよう、ターミナルに表示する)
- HTTP (`tailscale serve` を通さない直接の接続) では、PIN と Cookie が平文で流れる。tailnet の通信は WireGuard で暗号化されているが、LAN で `--host 0.0.0.0` を使う場合は傍受されうる。README で `tailscale serve` を引き続き推奨する
- 一人で使うときにも PIN の入力が要る。不便なら、無効にするオプション (`--no-pin`) を後で検討する
