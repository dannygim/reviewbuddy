# データモデル

**目的: セッションごとの `review.db` に保存するスレッドとコメントのスキーマと、ファイルが変わったときにコメントの位置を追従させる再アンカーの規則を定める。**

- 対象の要件: F10 / F11 / A2 / A3 ([要件.md](./要件.md))
- 保存場所とセッションの単位は [保存先とセッション.md](./保存先とセッション.md) を参照

***

## スキーマ (`review.db`)

```sql
CREATE TABLE threads (
  id           TEXT PRIMARY KEY,              -- 時系列で並ぶ ID (ULID 形式)
  file_path    TEXT NOT NULL,                 -- ルートからの相対パス・POSIX 区切り
  start_line   INTEGER NOT NULL,              -- 1 始まり
  end_line     INTEGER NOT NULL,              -- 両端を含む
  anchor_text  TEXT NOT NULL,                 -- 作成時点の選択行の内容 (プロンプトに使う)
  file_sha     TEXT NOT NULL,                 -- 作成時点のファイルの内容のハッシュ (SHA-256)
  origin_view  TEXT NOT NULL,                 -- 'source' | 'preview'
  status       TEXT NOT NULL DEFAULT 'open',  -- 'open' | 'resolved'
  outdated     INTEGER NOT NULL DEFAULT 0,
  created_by   TEXT NOT NULL,
  created_at   TEXT NOT NULL,
  resolved_by  TEXT,
  resolved_at  TEXT,
  exported_at  TEXT                           -- 最後にプロンプトとしてコピーされた時刻
);

CREATE TABLE comments (
  id          TEXT PRIMARY KEY,
  thread_id   TEXT NOT NULL REFERENCES threads(id) ON DELETE CASCADE,
  author      TEXT NOT NULL,                  -- Nickname (自己申告)
  client_id   TEXT NOT NULL,                  -- ブラウザごとのランダムな ID (自分のコメントかの判定用)
  body        TEXT NOT NULL,
  created_at  TEXT NOT NULL,
  updated_at  TEXT
);

CREATE INDEX idx_threads_file ON threads (file_path, start_line);
CREATE INDEX idx_comments_thread ON comments (thread_id, created_at);
```

- スレッドの 1 件目のコメントが元コメント、2 件目以降がリプライ
- 編集・削除は自分の `client_id` で書いたコメントだけ (信頼ベースの簡易な制御)。元コメントはリプライが無いときだけ消せて、消すとスレッドごと消える
- 日時は UTC の ISO 8601 (`2026-10-23T06:30:12.345Z`)
- 開くときの設定: `PRAGMA journal_mode = WAL`、`PRAGMA foreign_keys = ON`、`PRAGMA busy_timeout = 5000` (サーバーの起動中に `akapen export` が読むため)
- スキーマの版は `PRAGMA user_version` で管理し、開くときに順番にマイグレーションする
- **JSONL を採らない理由**: 編集・Resolve・削除が「追記」で表せず、イベントソーシングにすると読み出す側が複雑になる。代わりに `akapen export --format jsonl` で書き出せるようにする ([プロンプト出力仕様.md](./プロンプト出力仕様.md))

## 再アンカー (A2)

ファイルが変わると行番号がずれる。スレッドごとに、作成時の `anchor_text` を新しい内容から探し直して行範囲を更新する。

1. 新しい内容の `start_line .. end_line` が `anchor_text` と一致する → そのまま (`outdated = 0`)
2. 一致しない → 新しい内容の中で、`anchor_text` と行単位で完全に一致する範囲をすべて探す
   - 1 つ以上ある → 元の `start_line` に最も近いもの (同じ距離なら前のもの) に行範囲を更新し、`outdated = 0`
   - 無い → 行範囲はそのままにして `outdated = 1`
3. ファイルが削除された → `outdated = 1`

- 常に `anchor_text` (作成時点の内容) と比べる。いったん Outdated になったスレッドも、内容が戻れば再び追従する
- 行の比較は完全一致 (前後の空白も含む)。迷うくらいなら Outdated に倒す (誤った行に付け替えるより安全)
- 行範囲や `outdated` が変わったスレッドは `thread.updated` で配信する

***

## テスト観点

- スキーマの作成とマイグレーション (`user_version` が上がる)
- 元コメントとリプライの順序、`ON DELETE CASCADE`
- 他人の `client_id` のコメントを編集・削除できない。リプライのある元コメントは消せない
- 再アンカー: 上に行を挿入 → 下にずれる / 上の行を削除 → 上にずれる / 対象の行を編集 → Outdated / 対象の行を削除 → Outdated / 同じ内容が 2 か所 → 近いほうに付く / 内容が戻る → Outdated が外れる
