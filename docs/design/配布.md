# 配布

**目的: akapen を mise で入れられる単一バイナリとして配る方式、リリースの手順、利用側の設定、private リポジトリのまま使うときの条件を定める。**

- 対応する調査: [mise_配布_調査.md](../research/mise_配布_調査.md) / [Bun_調査.md](../research/Bun_調査.md)

***

## 方針

**GitHub Releases に OS / アーキテクチャ別の単一バイナリを置き、mise の `github:` バックエンドで入れる。public にした後に packslip (署名付きのリリースマニフェスト) を足す。** `mise use akapen` の短縮名は、mise registry の条件 (通常は数千スター、継続的なメンテナンス、作者以外での利用実績) を満たしてから検討する。

***

## 方式の比較

| 方式 | 利用者のコマンド | 公開側に必要なもの | 長所 | 短所 |
|------|----------------|------------------|------|------|
| **`github:`** (第 1 段階) | `mise use -g github:<owner>/akapen` | Releases に OS / arch 別のアーカイブ | すぐ使える。利用側に Bun が要らない。GitHub のダイジェスト・checksum・artifact attestation を mise が検証する | 1 バイナリが 100MB 前後 |
| **`packslip:`** (第 2 段階) | `mise use -g packslip:github.com/<owner>/akapen` | 上記 + `jdx/packslip@v1` Action による署名マニフェスト | 署名の検証が強い。man ページ・補完・agent skill の同梱も宣言できる。mise registry の Tier 1 | 2026 年に出た新しい仕組みで事例が少ない |
| `npm:` | `mise use -g bun npm:akapen` (`npm.package_manager = "bun"`) | npm への公開 | 数百 KB と軽い | 利用側に Bun のランタイムが要る。registry では Tier 4 |
| `http:` | `mise.toml` に URL のテンプレートを書く | 任意の配布先 | 社内のストレージなどにも置ける | 利用者側の設定が長い。バージョンの一覧に別の URL が要る |
| 短縮名 | `mise use -g akapen` | mise registry への PR (`registry/akapen.toml`) | 最も簡単 | 人気の条件が高く、多くは却下される |

## CI とリリース (GitHub Actions)

### CI (push のたび)

- `main` への push と Pull Request で、`ubuntu-latest` と `macos-latest` で `bun run verify` を実行する
- Bun のバージョンは `mise.toml` に合わせる (`jdx/mise-action` で入れる)

### リリース (タグ `v*` の push)

1. タグと `package.json` の `version` が一致することを確かめる (違えば失敗)
2. ビルドする。`linux-x64` / `linux-arm64` は Linux のランナーで `--target` を使ってクロスコンパイルし、`darwin-arm64` は macOS のランナーでビルドする

   ```sh
   bun build src/cli.ts --compile --minify --sourcemap \
     --no-compile-autoload-dotenv --no-compile-autoload-bunfig \
     --target=bun-darwin-arm64 --outfile dist/akapen
   ```

3. macOS 版は `codesign` で署名する (Bun のドキュメントが推奨する JIT 用の entitlements 付き。Developer ID を持たないため ad-hoc 署名)。ブラウザ経由で配らない限り、公証は要らない見込み
4. `akapen-v0.1.0-darwin-arm64.tar.gz` のように、OS / arch をファイル名に含めて固める (中身は `akapen` の 1 ファイル)。mise の自動判定に任せられる
5. `checksums.txt` (SHA-256) を作る。artifact attestation (`actions/attest-build-provenance`) は public にしてから付ける
6. GitHub Release を作ってアップロードする
7. スモークテスト: Release から落としたバイナリで `akapen --version` がタグの版を出す
8. 第 2 段階 (public にした後): `jdx/packslip@v1` で `packslip.sigstore.json` を同じ Release に足す

## 利用側の設定

```toml
# 個人: ~/.config/mise/config.toml (mise use -g で自動で追記される)
[tools]
"github:<owner>/akapen" = "latest"

# チームのリポジトリで版をそろえる場合: mise.toml
[tools]
"github:<owner>/akapen" = "0.1"
```

- `mise lock` で `mise.lock` を作れば、チェックサムまで固定できる
- リポジトリが private の間は、利用者側に GitHub のトークンの設定が要る (次の節)

***

## private リポジトリのまま使う場合

**使える。** `github:` バックエンドは、トークンがあれば private リポジトリの Release も取得できる。

1. 認証を用意する (どちらか)
   - **gh を使う (おすすめ)**: `gh auth login` 済みにしておく。mise は gh の `hosts.yml` を (gh を実行せずに) 読む
   - **専用のトークン**: fine-grained PAT (対象のリポジトリのみ、Contents: Read-only) を `MISE_GITHUB_TOKEN` か mise の設定ディレクトリの `github_tokens.toml` に置く
2. `mise token github` で、どのトークンが使われるかを確かめる (マスク表示)
3. `mise use -g github:<owner>/akapen`

注意点:

- mise は最初に見つけたトークンだけを使う。期限切れの `GITHUB_TOKEN` などが環境変数に残っていると、gh の認証まで届かない
- artifact attestation は、private リポジトリでは GitHub Enterprise Cloud が要る → private の間は付けない。checksum の検証は効く
- 他のリポジトリの GitHub Actions から入れる場合は、ワークフローの `GITHUB_TOKEN` では届かないので、PAT か GitHub App のトークンが要る
- ブラウザで使うだけの同僚には、リポジトリの権限もトークンも要らない
- packslip が private で動くかは未確認 → public にしてから入れる

***

## 未確認の事項

- アセットの名前で、mise の自動判定が正しく選ぶか → 最初のリリースで `mise use` して確かめる
- mise で落としたバイナリに quarantine 属性が付かず、Gatekeeper の警告が出ないか → 最初のリリースで確かめる
