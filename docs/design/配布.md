# 配布

**目的: reviewbuddy を mise で入れられる単一バイナリとして配る方式、リリースの手順、利用側の設定、GitHub のトークンが要る場合を定める。**

- 対応する調査: [mise_配布_調査.md](../research/mise_配布_調査.md) / [Bun_調査.md](../research/Bun_調査.md)

***

## 方針

**GitHub Releases に OS / アーキテクチャ別の単一バイナリを置き、mise の `github:` バックエンドで入れる。public にした後に packslip (署名付きのリリースマニフェスト) を足す。** `mise use reviewbuddy` の短縮名は、mise registry の条件 (通常は数千スター、継続的なメンテナンス、作者以外での利用実績) を満たしてから検討する。

***

## 方式の比較

| 方式 | 利用者のコマンド | 公開側に必要なもの | 長所 | 短所 |
|------|----------------|------------------|------|------|
| **`github:`** (第 1 段階) | `mise use -g github:<owner>/reviewbuddy` | Releases に OS / arch 別のアーカイブ | すぐ使える。利用側に Bun が要らない。GitHub のダイジェスト・checksum・artifact attestation を mise が検証する | 1 バイナリが 100MB 前後 |
| **`packslip:`** (第 2 段階) | `mise use -g packslip:github.com/<owner>/reviewbuddy` | 上記 + `jdx/packslip@v1` Action による署名マニフェスト | 署名の検証が強い。man ページ・補完・agent skill の同梱も宣言できる。mise registry の Tier 1 | 2026 年に出た新しい仕組みで事例が少ない |
| `npm:` | `mise use -g bun npm:reviewbuddy` (`npm.package_manager = "bun"`) | npm への公開 | 数百 KB と軽い | 利用側に Bun のランタイムが要る。registry では Tier 4 |
| `http:` | `mise.toml` に URL のテンプレートを書く | 任意の配布先 | 社内のストレージなどにも置ける | 利用者側の設定が長い。バージョンの一覧に別の URL が要る |
| 短縮名 | `mise use -g reviewbuddy` | mise registry への PR (`registry/reviewbuddy.toml`) | 最も簡単 | 人気の条件が高く、多くは却下される |

## CI とリリース (GitHub Actions)

### CI (push のたび)

- `main` への push と Pull Request で、`ubuntu-latest` と `macos-latest` で `bun run verify` を実行する
- Bun のバージョンは `mise.toml` に合わせる (`jdx/mise-action` で入れる)

### リリース (タグ `v*` の push)

1. タグと `package.json` の `version` が一致することを確かめる (違えば失敗)
2. ビルドする。`linux-x64` / `linux-arm64` は Linux のランナーで `--target` を使ってクロスコンパイルし、`darwin-arm64` は macOS のランナーでビルドする

   ```sh
   bun scripts/build.ts --target bun-darwin-arm64 --outfile build/reviewbuddy
   ```

   `scripts/build.ts` は `bun run build` と同じ設定 (`--splitting` / `--minify` / `--sourcemap`、`.env` と `bunfig.toml` の自動読み込みを無効) でビルドする。ワークフローは `.github/workflows/release.yml`

3. macOS 版は `codesign` で署名する (Bun のドキュメントが推奨する JIT 用の entitlements 付き。Developer ID を持たないため ad-hoc 署名)。ブラウザ経由で配らない限り、公証は要らない見込み
4. `reviewbuddy-v0.3.0-darwin-arm64.tar.gz` のように、OS / arch をファイル名に含めて固める (中身は `reviewbuddy` の 1 ファイル)。mise の自動判定に任せられる
5. `checksums.txt` (SHA-256) を作る。artifact attestation (`actions/attest-build-provenance`) は public にしてから付ける
6. GitHub Release を作ってアップロードする
7. スモークテスト: Release から落としたバイナリで `reviewbuddy --version` がタグの版を出す
8. 第 2 段階 (public にした後): `jdx/packslip@v1` で `packslip.sigstore.json` を同じ Release に足す

***

## 利用側の設定

```toml
# 個人: ~/.config/mise/config.toml (mise use -g で自動で追記される)
[tools]
"github:<owner>/reviewbuddy" = "latest"

# チームのリポジトリで版をそろえる場合: mise.toml
[tools]
"github:<owner>/reviewbuddy" = "0.1"
```

- `mise lock` で `mise.lock` を作れば、チェックサムまで固定できる
- 利用者側に GitHub のトークンは要らない (次の節)

***

## GitHub のトークン

**利用者にトークンは要らない。** リポジトリは public で (2026-10-27 から。それまでは private)、mise は public な Release をトークンなしで入れる ([mise_配布_調査.md](../research/mise_配布_調査.md))。トークンを渡すのは、GitHub の匿名のレート制限で mise が `403 Forbidden` になったときだけとする。

1. トークンを渡す (どちらか)
   - **gh を使う**: `gh auth login` 済みにしたうえで、mise に gh からトークンをもらうよう設定する: `mise settings set github.credential_command 'gh auth token --hostname "$MISE_CREDENTIAL_HOST"'`。gh は macOS では通常トークンをキーチェーンに保存するため、mise が読む gh の `hosts.yml` にはトークンが無い (2026-10-23 に手元で確認。`mise token github` が `(none)` になる)
   - **トークンを置く**: `MISE_GITHUB_TOKEN` か mise の設定ディレクトリの `github_tokens.toml` に置く
2. `mise token github` で、どのトークンが使われるかを確かめる (マスク表示)

注意点:

- mise は最初に見つけたトークンだけを使う。期限切れの `GITHUB_TOKEN` などが環境変数に残っていると、そちらが使われて失敗する
- リリースのスモークテスト (GitHub Actions) は、ワークフローのトークンを `MISE_GITHUB_TOKEN` に渡し、`attestations: read` の権限を付けている。権限が無いと、mise が attestation を API で確かめるところで 403 になる
- ブラウザで使うだけの同僚には、トークンは要らない
- artifact attestation と packslip は、public になったので付けられる (artifact attestation は、Free / Pro / Team では public リポジトリのみ)。まだ付けていない (リリースの流れの 5 と 8)
